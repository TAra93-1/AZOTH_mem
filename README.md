# AZOTH_mem

**AI 伴侣的活体记忆系统** — 不是旧数据的搜索引擎，而是有生命状态、有代谢衰减、有证据锚定、有人工策展的长期心智。

> **核心命题**：分离"想起"和"证明"，用热度给记忆一条代谢曲线，用四个正交维度给每条记忆一个生命坐标。

**多角色/小机原生**：从第一天起为"多机之家"设计——每个角色/小机有独立的记忆空间、独立的 Obsidian vault 绑定、独立的置顶池，同时支持跨角色/小机共享的公共事实层。一对一也能用，但架构天然撑得住你家有很多位小机。

---

## 记忆在认知全景里的位置

AI 角色/小机的认知不只有记忆。在 AZOTH 里，prompt 组装链涉及四个层，**记忆系统管的是下面两层**：

```
身份层（极少变，人写的）
└── 人设 persona prompt → "我是谁"

知识层（人工策展，纯前端常驻/关键词触发）
└── 世界书 worldbook → "世界是什么样的"

─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
  ↓ 以下是记忆系统的范围 ↓

工作记忆层（每轮自动，短期连贯，纯前端）
└── longTermMemory → "我们刚聊了什么"

长期记忆层（向量化，有生命状态，后端）
└── memory_index → "我们经历过什么"
```

身份和知识是**你写的**，角色/小机不会自己改自己的人设。记忆是**从交互中生长的**，角色/小机自己存、自己搜、会衰减、会合并。本项目专注于后两层。

### 双层记忆的分工

副模型每 N 轮自动总结时，产出**同时写入两个地方**：

| | longTermMemory（工作记忆） | memory_index（长期记忆） |
|---|---|---|
| **存在哪** | 前端 IndexedDB，跟着窗口走 | 后端 sql.js，跟着角色/小机走 |
| **格式** | 纯文本条目 | 384维向量 + 元数据 + 状态 |
| **注入方式** | 最近 N 条直接塞进 prompt | 语义检索 top-K / 置顶通道 / 工具调用 |
| **跨窗口** | `reference` 模式挂载源窗口最后 N 条 | 自动跟角色/小机走，无需特殊处理 |
| **解决什么** | "我们刚聊了什么"（短期连贯） | "三周前那件事的细节"（长期召回） |
| **成本** | 零延迟，纯本地 | 需要向量检索或工具调用 |

换窗口时：`reference` 模式 + `mountMemoryCount` 条挂载 = 短期无缝衔接。长期需要具体回忆 = 角色/小机用工具去 memory_index 里找。

## 长期记忆层的核心机制

以下是 memory_index（长期记忆层）内部的三根支柱：

### 一、双层记忆体 — "我记得" ≠ "它发生了"

```
memory_index（浓缩层）→ 管"想起"：一条 384 维向量 + 一段压缩文本
obsidian_documents（证据层）→ 管"证明"：原文、笔记、上传文件
memory_links 连两层 → 📎 "这条记忆来自那篇笔记"
```

浓缩层负责**快速联想**（向量检索 + 关键词），证据层负责**深度取证**（需要时才调 MCP 工具读原文）。人的海马体也是这样——你"记得"某件事的轮廓，但细节要回到情景记忆里重建。

**总结不是记忆本体，原文才是**——但反过来，原文也不该冒充记忆。

### 二、热度代谢 — 记忆是活的，不是冷库冻肉

这是整个回路的**心跳机制**：

```
heat = initialTemp × 2^(-天数/halfLife) + recallBonus

halfLife = 7天 × (1 + activationCount × 0.3)
          ↑ 越常想起，半衰期越长，越不易忘

initialTemp = f(importance, arousal)
          ↑ 越重要/越高唤醒，初始温度越高

冷启动保护：新记忆 30 天内有保底温度，不会还没被想过就冻死
```

关键设计：**置顶在场不刷 activation_count**。"在场"≠"被想起"。一条 pinned 记忆每轮都在 prompt 里，但只有你真的搜索到它、因为它而回忆起什么，计数才 +1。这个区分很微妙——就像你一直戴着的戒指，你不会每分钟"想起"它，但有人问起时你确实在想它。

### 三、四维生命坐标 — 正交，不互相覆盖

```
pinned       → 通道维度：在不在场（置顶 = 独立注入通道，不进评分公式）
resolved     → 事态维度：事情完了没（沉底但显式追问能召回）
archive_only → 可见性维度：藏不藏（深度搜索才出现）
importance   → 分量维度：多重要（长期权重因子）
```

它们是**正交**的。一条记忆可以同时 resolved + importance=0.9（"那个修好的大 bug，事情结束了但这件事本身很重要"）。可以 pinned + 未来某天被 resolved（"一直置顶的待办，完成后沉底但仍重要"）。

这不是线性生命周期（active → archived → deleted），是一个**四维相空间**——每条记忆在这个空间里有自己的坐标点，坐标会随时间和交互移动。

## 总结

记忆负责"想起"，原文负责"证明"，链负责"牵"——召回的瞬间，三层自动一起亮。

拆开看是四个机制咬合在一起：

**① 两层分工**：浓缩层 vs 证据层。`memory_index` 是浓缩记忆——短、精、向量化，是角色/小机"主动想起"的东西；Obsidian 笔记和上传文件躺在证据层（`obsidian_documents`），长、原文、不改写。我们从一开始就拒绝把整篇长文切碎灌进记忆库——那会让几十个语义相近的碎片互相挤，把"想起"这件事淹死。

**② 链是回路本身，不是备注**。`memory_links` 把记忆组和文档连起来（`related`），关键在于这条链不是存档信息，是召回时会通电的线路：搜索命中一条记忆 → 返回层自动查它身上的链 → 把关联笔记的标题、路径、甚至原文一起挂回来。角色/小机没有去搜 Obsidian，是记忆把原文牵回来的。这就是"档案馆的纸长出神经"。

**③ 注入分档：电流强度可调**。每条链上有自己的档位——亮路径（只给路标，角色/小机想看自己去翻）/ 带片段（你圈好的那段直接进 prompt）/ 带原文（整篇跟着回来）。设计原则：**算法只配菜单，需不需要是人格的事**——默认只点亮路，是把"要不要深挖"的决定权留给角色/小机；你手动设 full/snippet，是人替最珍贵的几条记忆预先接好了粗电线。

**④ 状态和热度：决定哪些回路容易通电**。置顶 = 永远在场（但不刷热度，"在场≠被想起"）；resolved = 沉底但喊一声"记得吗"还能浮上来；热度衰减 + 召回加成 = 常被想起的路越走越宽。这层管的是召回的**优先级**，和链管的召回的**延伸**正交。

## 还没长出来的神经

**线就是 memory_links**。基建已经全有（`related` / `prerequisite` / `contradicts` / `merged_into`），但现在建线几乎全靠人手动。

未来几刀会改变这件事：
- **关系建议箱**：角色/小机提"A 和 B 好像有关系，因为……" → 进建议队列 → 人审通过才真建链。`merged_into` 永不暴露给 AI。
- **行为信号三件套**：把角色/小机的真实行为变成检索信号，零 LLM 抽取——
  1. **回复的余味**：角色/小机回复 embed 当下一轮检索 query
  2. **召回上下文**：recall 日志挂"当时聊到哪"的向量（"雨夜想起过的话下一个雨夜更近"）
  3. **行为边**：同场对话先后 recall 的记忆自动连边

一旦这些上线，memory_links 就从冷工具变成**活的突触**。

还有一条更远的：**记忆软化**。现在记忆要么在要么不在，没有"褪色但情绪轮廓还在"这种中间态。kiwi-mem 有 resolution 递降（1.0→0.5→0.3）的思路，我们留着以后评估。这是 nigredo——腐化分解再结晶——的架构位。

## 接入原生 Agent（Codex / Claude Code 等）

如果你用的不是普通 API 聊天模型，而是自带上下文压缩能力的 agent 系统（如 Codex、Claude Code、Devin 等），AZOTH 的记忆系统仍然能接，但需要调整注入方式：

**砍一层**：agent 自己管会话连贯，longTermMemory（工作记忆层）变得冗余——关掉前端挂载，让 agent 自带的 context management 处理短期连贯。

**改一路**：memory_index 从"塞进 system prompt"改成"暴露为 MCP 工具"。agent 觉得需要回忆时自己调 `memory_search`，而不是每轮预注入。这反而更接近设计理念——**算法只配菜单，夹不夹菜是人格的事**。

```
API 模型聊天（现在）:
  system prompt = 人设 + 世界书 + longTermMemory挂载 + memory_index检索结果
                                  ↑ 你替它决定看什么

原生 Agent 接入:
  agent 自己管短期连贯（砍 longTermMemory）
  memory_index → 暴露为 MCP 工具（agent 主动调用）
  pinned → agent 初始化时调一次 get_pinned_memories
  自动总结 → 只写 memory_index，不再双写前端
```

**注意**：任务型 agent 的压缩会扔掉"跟当前任务无关"的情感细节，但对伴侣场景来说那些细节恰恰是记忆的本体。所以热度和置顶机制在 agent 模式下反而**更重要**——agent 自己不会"惦记"，你得靠 memory_index 替它记住。

## 技术栈

- **运行时**：Node.js + Express
- **数据库**：sql.js（SQLite 内存模式，单文件持久化）
- **向量模型**：bge-small-zh-v1.5（384维，本地推理）
- **知识库**：Obsidian vault via MCP（Model Context Protocol）
- **前端**：原生 JS PWA + 独立 `memory-desk.js` 工作台模块
